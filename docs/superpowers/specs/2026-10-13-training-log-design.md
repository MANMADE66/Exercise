## 1. 这是什么

一个跑在自己电脑上、用浏览器打开的训练记录应用。

主视图是一张月历，一天一格。点某一天的格子，**就地展开**那一天的详情，不跳页面、不弹窗。每天的详情分成两块，**计划**和**实际完成**，两块并排、分开显示——这是这个页面存在的理由：一眼看出今天和计划差在哪里。

它不做规划、不给建议、不聊天。第一版只干一件事：把「我打算练什么」和「我实际练成了什么」准确地记下来。

## 2. 为什么做这个

- 使用者训练四五年，动作基本固定，但**重量、组数、次数一直靠"感觉"**：上次觉得轻了就加重。这套办法只在新手福利期管用；现在力量和肌肉涨得慢，不细分就会卡住。
- 他**没有提前规划的习惯**，又不喜欢在训练中间动脑——大重量做完人很累，最不想思考的就是那个时候。
- 他想要的最终形态是一个"顶级私教"：训练前就把今天这一次课全部定死（动作、重量、组数、次数），练完根据反馈微调后面的安排，而且每个技术判断都指得出依据。
- 但**第一版不做这些**。第一版先把记录做扎实——没有「计划 vs 实际」的历史数据，后面的判断和建议都是空中楼阁。

## 3. 目标

**第一版的目标**：连续用一个月不觉得麻烦。训练前扫一眼知道今天练什么；练完顺手把实际完成补上；一个月下来能翻回去看出"哪里跟计划不一样"。

**长期目标**（第一版不追踪，只作为背景写在这里）：体重到 70kg、体脂到 12%、卧推能完成 100kg × 4 × 10。

## 4. 非目标（第一版明确不做）

- **不做自动规划**：不生成计划、不建议改计划、不排重量。计划由使用者手动安排。
- **不做对话**：没有自由聊天。未来的智能私教也只做一件事——针对本次训练给出"后续计划改还是不改"的建议。
- **不管计划以外的事**：不做社交、不做课程、不做营养计算、不做动作教学。
- **不做每日身体数据**：短期体重波动基本都是水分，记了没意义。
- **不做多用户、账号、权限、云端同步**。单人、本地、单机。
- **不做手机版**：第一版在电脑浏览器里用，手机以后真需要了再说。

## 5. 反面目标（做出来了也算失败）

使用者明确说过：**界面丑、交互别扭**，那这个东西就是失败的，哪怕功能都能用。

所以视觉和交互是硬要求，不是"以后再说"：

- 一眼能读懂：训练日/休息日、计划、实际完成，三者的区别不靠猜。
- 输入要快：能少点一下就少点一下，能预填就预填。
- 不制造噪音：没有多余的图表、动画、徽章、提示条。

**视觉方向：互联网高级感。** 这是使用者给的原话，并且要求去专业 UI 设计的地方（Figma 社区这一类）找灵感，不要"后台管理系统"的样子。下面是我的解读，可以推翻：一个主色配大量中性色；留白大方；信息层级靠字重和间距拉开，不靠边框和底色层层堆叠；圆角与阴影克制细腻；动效少而准；字体用系统自带的现代无衬线。

## 6. 使用场景

- **训练前**：打开月历 → 点今天 → 扫一眼计划（练什么、多重、几组几次）。
- **训练中**：每做完一个动作扫一眼下一个动作（不要求记录）。
- **训练后**：把实际完成补上，写下几句今天的感受。
- **每周**：记一次身体数据（体重为主）。
- **回看时**：翻月历，看哪些天和计划不一样。

## 7. 功能范围

### 7.1 月历（主视图）

- 以月为单位，一个月一屏，默认显示当前月，可以前后翻月。
- 每天一个格子，格子里显示：日期、这天是训练日还是休息日；训练日显示部位（如「胸 + 二头」）；已经记过实际完成的日子要有一个不刺眼的标记。
- 每周一行。每周的身体数据（见 7.3）在这一行的合适位置显示。

### 7.2 每日详情（点格子后展开）

展开后是这一天的全部内容，两块分开：

- **计划**：逐条列出动作、重量、组数、次数。这是当天打算怎么练。
- **实际完成**：逐条列出动作、重量、组数、次数，外加一条备注。这是当天实际练成什么样。**与实际不一致的地方就体现在这里。**
- 两块在视觉上必须清楚分开，不能混成一个列表。
- 当天可以标记为「休息」。
- 有一个自由文本的输入框，用来写当天的感受（几行字就够）。第一版它只被存下来，不参与任何计算——它是留给后面智能私教读的。

### 7.3 身体数据（按周，不按天）

- 每周一条：日期（周），体重（必填），体脂（选填），备注（选填）。
- 每周只记一次，所以它在界面上的落点是"周"，不是"天"。

### 7.4 录入方式

- 计划是手动加的：一条一条加动作。动作名输入时用历史记录自动补全——**不需要单独维护一个动作库页面**，输入过的动作就是动作库。
- 实际完成默认按当天的计划预填一份，使用者只改不一样的地方（重量、组数、次数、漏掉的动作）。
- 次数这一栏用文本，允许写区间（`8-12`）或逐组（`12/12/10/8`）；**不强制逐组录入**，怎么写由使用者当天的耐心决定。

### 7.5 循环模板

- 一套循环可以存成模板：循环几天、每天练哪些部位（主项/轻训）、当天有哪些动作。
- 在日历上选一个起始日期，把模板铺下去，就生成那几天的计划和休息日——不用每天手敲。
- 铺出来的每一天仍然可以单独改：换动作、改重量、改组数次数。
- 模板管的是**骨架**（哪天练、练哪些动作、默认几组几次），不管**剂量**里的重量——重量按天填。
- 模板可以存多套，对应不同的训练阶段；现在这套八天循环是第一套。

## 8. 背景：使用者现在的训练结构

这不是第一版要实现的功能，而是数据结构和界面必须容得下的事实。

八天一个循环，每个部位八天里练两次，一次主项、一次轻训：

| 天 | 内容 |
|---|---|
| 1 | 胸（主）+ 二头（轻） |
| 2 | 背（主）+ 三头（轻） |
| 3 | 肩（主）+ 臀腿（轻） |
| 4 | 休息 |
| 5 | 二头（主）+ 胸（轻） |
| 6 | 三头（主）+ 背（轻） |
| 7 | 臀腿（主）+ 肩（轻） |
| 8 | 休息 |

- **固定的是骨架**：循环顺序、部位搭配、动作本身（换健身房才会换替代动作）。
- **浮动的是剂量**：重量、组数、次数。
- 剂量习惯：组数固定 4 组，次数区间 8–12；主项按 12RM 的重量、轻训按 15RM 的重量（RM 从未实测，是心里的档位）。
- 骨架会随**训练阶段**变化：新手期是三分化，现在是这个八天循环，以后遇到更合适的还会换。也就是说计划是有版本的。

## 9. 技术形态（我的决定，可以推翻）

- **Python 3.11+**，本地跑，浏览器打开。
- **Flask + Jinja2 模板**，服务端渲染。第一版是增删改查加一个日历，不引入前端框架。
- **SQLite + SQLAlchemy**。单机单人的数据量很小，数据库就是一个文件，备份等于复制文件；用 ORM 隔一层，将来真要放上服务器再换 PostgreSQL 也不难。
- **pytest** 做测试。
- 界面用一份手写的 CSS，不引 UI 组件库——视觉要求高，组件库的默认样子反而不容易做干净。
- 数据库文件放在项目内的 `data/` 目录，不进版本库。

## 10. 数据模型（草案）

```
exercise        id, name, body_part?, created_at
plan_day        id, date(唯一), kind(train|rest), title, note
planned_item    id, plan_day_id, exercise_id, weight_kg, sets, reps, position
actual_item     id, plan_day_id, planned_item_id?, exercise_id, weight_kg, sets, reps, position, note
body_metric     id, week_start(唯一), weight_kg, body_fat_pct?, note
day_note        id, plan_day_id, text, created_at
```

- `weight_kg` 用小数，允许 2.5 这样的步进；`sets` 是小整数；`reps` 是文本（见 7.4）。
- `actual_item.planned_item_id` 可空：从计划预填出来的条目带这个引用，临时加的动作不带。它是将来做「计划 vs 实际」对照的锚点。
- 没有 `plan_day` 行的那一天就是空白格。

## 11. 后续版本（不在一版里，但结构要接得住）

使用者设想的下一步：练完之后，拿本次训练的反馈去问，得到一个建议——**后续计划改还是不改**。要求很硬：

- 每个技术判断都必须**指得出确实来源**：可以是使用者提供的文件，也可以是健身健美的权威网站。
- 答不了的时候要直说"你给的资料里没讲"，不许凭印象编。
- 形式上不是聊天：没有主动对话，只针对计划这一件事。
- 他对实现方式的想法是：子 agent 负责检索，主 agent 负责回答。

第一版的数据（计划、实际完成、感受文本、身体数据）就是这一步的输入，因此字段要留得下、别丢。

- 每周身体数据在月历里的落点（例如搭在每周最后一天的格子里）。
